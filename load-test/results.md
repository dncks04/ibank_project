# 부하 측정 기록

같은 조건으로 구조 변경 전후를 비교하기 위한 기록이다. 수치는 측정한 PC와 디스크에 크게 좌우되므로,
절대값보다 **같은 환경에서 잰 값끼리의 차이**를 본다.

## 측정 조건 (공통)

| 항목 | 값 |
|---|---|
| 시나리오 | `load-test/transfer-load.js` — 50 VU가 같은 출금 계좌 한 곳에서 1원씩 동시 이체 (단일 행 락 최악 경합) |
| 시간 | 워밍업 15초 1회 후, 30초씩 3회 |
| DB | Docker `postgres:16-alpine`, 측정 전용 컨테이너(빈 DB에서 시작) |
| 앱 | 로컬 JVM(Java 21)에서 `java -jar`, 기본 프로파일, 커넥션 풀 20 |
| Redis·호출 제한·FDS | 모두 비활성(기본값) |

앱을 컨테이너가 아니라 로컬 JVM으로 띄운 이유: 측정 당시 Gradle 배포판 서버 연결이 느려 이미지 빌드가 되지 않았다.
이후 측정도 같은 구성으로 맞춘다.

**기준값: 약 77 TPS, p95 약 1.0초.** 세 회차 모두 종료 후 `A + B = 100,000,000`으로 초기 총액과 일치했다.

회차가 갈수록 조금씩 빨라지는 것은 JIT 워밍업이 15초로는 다 끝나지 않기 때문으로 보인다(원인을 따로 검증하지는 않았다).
스크립트의 임계값 `p95 < 800ms`는 이 환경에서 세 회차 모두 넘었다. 임계값은 그대로 두었다.

## 2단계 거래 처리 (2026-11-14)

이체를 가승인 → 판정 → 확정으로 나눈 뒤 같은 시나리오를 다시 쟀다. 앱은 `ibank.fds.mode=http`로 띄우고,
[FdsStub.java](FdsStub.java)를 FDS 서비스 대역으로 붙여 응답 지연만 바꿨다. 조건마다 빈 DB에서 시작했다.

| 조건 | FDS 대역 | ibank 설정 |
|---|---|---|
| 지연 0ms | 즉시 APPROVE | 연결·응답 타임아웃 각 300ms |
| 지연 100ms | 100ms 뒤 APPROVE | 같음 |
| 타임아웃 | 5초 뒤 응답(응답 타임아웃 초과) | 같음. 서킷 브레이커 기본값(최근 20건 중 최소 10건, 실패율 50%, 열림 10초) |

같은 날 기준 jar(`base-ibank`)도 같은 방식으로 다시 쟀다. 3일 전 측정(약 77 TPS)보다 높게 나와서,
비교는 같은 날 잰 값끼리 한다.

**기준 약 98 TPS(p95 약 0.68초) → 2단계 약 43~47 TPS(p95 약 1.3초).** 같은 계좌 한 곳에 몰리는 최악 경합에서는 처리량이 절반 아래로 떨어졌다.

읽은 것:

- **FDS 응답 지연은 처리량을 거의 바꾸지 않았다.** 지연 0ms와 100ms의 결과가 사실상 같다. 판정을 락 밖에서 기다리기 때문에,
  한 이체가 FDS 응답을 기다리는 동안 다른 이체가 계좌 락을 쓴다. 판정을 락 안에서 기다리는 구조였다면 락을 쥔 시간이
  건당 100ms를 넘으므로, 100ms 지연만으로 이 계좌의 처리량 상한이 초당 10건 아래가 된다.
- **FDS가 응답하지 않아도 거래는 멈추지 않았다.** 타임아웃 조건의 이체 4,597건이 모두 대체 정책으로 승인(`decisionSource=FALLBACK`)됐다.
  처음 몇 건만 응답 타임아웃(300ms)을 기다렸고 그 뒤로는 서킷 브레이커가 열려 FDS를 부르지 않고 바로 대체 정책으로 넘어갔다.
  로그상 서킷은 10초마다 반열림으로 바뀌어 시험 호출을 보내고 실패하면 다시 열렸다.
- **처리량이 줄어든 원인은 판정이 아니라 락 구간이다.** 이체 한 건이 출금 계좌 락을 두 번(가승인, 확정) 잡고,
  그 사이 홀드 기록·해제, 판정 결과 저장, Outbox 이벤트 두 건이 더 쓰인다. 계좌 한 곳에 몰린 요청은 이 락에서 줄을 서므로
  락 구간이 길어진 만큼 처리량이 줄어든다. 두 번의 락과 추가 쓰기 중 어느 쪽이 더 큰지는 따로 나눠 재지 않았다.
- 출금 계좌가 서로 다른 일반적인 부하에서는 이 줄서기가 없으므로 같은 비율로 떨어지지는 않는다. 다만 그 시나리오는 이번에 재지 않았다.
- 2단계 지연 0ms의 1회차가 유독 느린 것은 워밍업 15초가 2단계 경로의 JIT를 다 덥히지 못했기 때문으로 보인다(따로 검증하지 않았다).

재현:

```bash
java load-test/FdsStub.java 18090 100
java -jar build/libs/ibank_project-0.0.1-SNAPSHOT.jar --ibank.fds.mode=http --ibank.fds.base-url=http://127.0.0.1:18090 --ibank.fds.api-token=perf
k6 run -e DURATION=30s load-test/transfer-load.js
```
