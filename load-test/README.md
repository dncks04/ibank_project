# 부하 테스트 (k6)

동시 이체 상황에서 **처리량**과 **잔액 정합성**을 동시에 측정합니다.

## 시나리오

다수의 가상 사용자(VU)가 **동일한 출금 계좌 A**에서 입금 계좌 B로 1원씩 동시에 이체합니다.

- 모든 이체가 A 계좌 하나에 `SELECT ... FOR UPDATE` 락을 집중시켜 **최악의 락 경합(완전 직렬화)** 상황을 만듭니다.
- 각 요청은 고유 멱등성 키를 사용합니다.
- 종료 후 `(A 잔액 + B 잔액)`이 초기 총액과 **정확히** 일치하는지, A가 음수가 되지 않았는지 검증합니다.

## 실행

먼저 PostgreSQL과 애플리케이션을 띄운 뒤([메인 README의 실행 방법](../README.md#실행-방법)):

```bash
# 기본 (50 VU, 30초)
k6 run load-test/transfer-load.js

# 파라미터 지정
k6 run -e VUS=100 -e DURATION=1m -e BASE_URL=http://localhost:8080 load-test/transfer-load.js
```

## 결과 (50 VU · 30초, 로컬: PostgreSQL 16 컨테이너)

| 지표 | 값 |
|------|----|
| 총 이체 건수 | **2,639건** |
| 처리량 | **~84 TPS** (단일 계좌 직렬화 기준) |
| 실패율 | **0.00%** (2,645건 중 0건 실패) |
| 응답시간 | avg 572ms · med 546ms · p95 **799ms** · max 1.21s |
| **잔액 정합성** | **A 99,997,361 + B 2,639 = 100,000,000 = 초기 총액** ✓ |
| A 잔액 음수 | 발생하지 않음 ✓ |

### 해석 (면접 포인트)

- **정합성 100%**: 2,639건의 동시 이체가 **단 한 건의 lost update/중복 반영 없이** 정확히 반영됨. B가 받은 금액(2,639)이 정확히 이체 건수와 일치 → 비관적 락 + 트랜잭션 경계가 의도대로 동작.
- **처리량이 ~84 TPS인 이유**: 모든 요청이 **계좌 A 하나의 락을 두고 직렬화**되는 최악의 경합 시나리오이기 때문. 처리량은 애플리케이션이 아니라 **단일 행 락의 직렬 처리 속도**에 의해 제한됨(VU를 늘려도 TPS는 유지되고 대기 지연만 증가).
- **실무적 의미**: 서로 다른 계좌 쌍 간 이체는 락이 분산되어 훨씬 높은 처리량으로 확장됨. 즉 "정합성은 최악 경합에서도 보장, 처리량은 경합도에 비례"라는 트레이드오프를 실측으로 보여줌.

> 수치는 로컬 단일 머신(앱 + PostgreSQL 컨테이너) 기준이며 하드웨어에 따라 달라집니다. 위 스크립트로 누구나 재현할 수 있습니다.
