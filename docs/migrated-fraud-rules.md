# ibank에서 B 서비스로 이관하는 탐지 규칙

ibank(계정계)에 있던 룰 기반 이상거래 탐지 3종을 B(FDS·보호 흐름) 서비스로 옮긴다.
이 문서는 기존 구현(`base-ibank` 태그의 `FraudDetectionService`)의 로직과 기준값을 그대로 옮겨 적었다.
ibank에서는 해당 코드가 제거되고 B의 `POST /fds/evaluate` 판정으로 대체된다.

## 공통 사항

- 판정 대상은 **이체(TRANSFER)뿐**이었다. 출금(WITHDRAWAL)에는 적용되지 않았다. B에서는 둘 다 판정 요청이 온다.
- 여러 규칙이 동시에 걸릴 수 있고 하나라도 걸리면 보류(HELD)였다. 걸린 규칙 이름이 모두 기록됐다.
- 기존 구현은 출금 계좌의 DB 락을 쥔 상태에서 평가해 동시 요청에도 건수가 정확했다.
  B는 락 없이 평가하므로, **동시에 들어온 요청끼리는 서로를 못 볼 수 있다**(아래 VELOCITY 참고).
- 시각 기준: 기존 구현은 서버 로컬 시각을 썼다. B에서는 판정 요청의 `requestedAt`(Asia/Seoul 오프셋 포함)을 쓴다.

## 1. VELOCITY — 단시간 다회 출금

| 항목 | 값 |
|---|---|
| 사유 코드 | `VELOCITY` |
| 관찰 창 | 최근 5분 (`velocity-window-minutes=5`) |
| 임계 건수 | 5건 (`velocity-max-outgoing=5`) |

**조건**: 평가 시점 기준 최근 5분 동안 출금 계좌에서 출발한 거래 건수가 **5건 이상**이면 발동.

**세부 동작**
- 세는 대상은 `from_account_id`가 이 계좌인 모든 거래다. 이체와 출금이 모두 포함된다.
- **상태를 가리지 않는다.** 완료뿐 아니라 보류(HELD)·취소(CANCELLED)된 거래도 건수에 들어간다.
  즉 "시도 횟수"를 센다. 한 번 발동해 보류가 쌓이면 창이 지날 때까지 계속 발동한다.
- 지금 평가 중인 거래 자신은 아직 저장 전이라 건수에 포함되지 않았다. 그래서 실제로는 **6번째 시도부터** 걸린다.
- 금액 조건은 없다.

**B에서 구현할 때**: `GET /internal/accounts/{no}/transactions?from=...` 또는 이벤트로 쌓은 자체 이력으로 계산한다.
ibank 이력으로 계산하면 지금 판정 중인 거래(`PENDING_REVIEW`)가 이미 포함돼 있으므로 임계치를 "자기 포함 6건"으로 맞추거나 자기 자신을 빼야 한다.
동시에 판정 중인 다른 거래도 `PENDING_REVIEW`로 보이므로 누락은 줄어든다.

## 2. NIGHT_HIGH_VALUE — 심야 고액 이체

| 항목 | 값 |
|---|---|
| 사유 코드 | `NIGHT_HIGH_VALUE` |
| 심야 구간 | 0시 이상 5시 미만 (`night-start-hour=0`, `night-end-hour=5`) |
| 금액 임계 | 5,000,000원 이상 (`night-high-value-min=5000000`) |

**조건**: 요청 시각의 시(hour)가 심야 구간에 속하고 금액이 임계 이상이면 발동.

**구간 판정 규칙** (시작 포함, 종료 미포함)
- `start < end` (예 0~5): `start <= hour < end`
- `start > end` (자정 횡단, 예 23~6): `hour >= start` 또는 `hour < end`
- `start == end`: 빈 구간으로 보고 항상 미발동

분 단위는 보지 않는다. 04:59는 심야, 05:00은 아니다.

## 3. NEW_PAYEE_HIGH_VALUE — 신규 수취인 고액 이체

| 항목 | 값 |
|---|---|
| 사유 코드 | `NEW_PAYEE_HIGH_VALUE` |
| 금액 임계 | 3,000,000원 이상 (`new-payee-high-value-min=3000000`) |

**조건**: 금액이 임계 이상이고 출금 계좌에서 이 입금 계좌로 **완료(COMPLETED)된 이체가 한 건도 없으면** 발동.

**세부 동작**
- "이력"은 계좌 쌍(출금 계좌 → 입금 계좌) 단위다. 고객 단위가 아니다.
  같은 고객의 다른 계좌에서 보낸 적이 있어도 이 계좌에서는 신규 수취인이다.
- 방향이 있다. 상대가 나에게 보낸 이력은 세지 않는다.
- 완료된 것만 센다. 보류·취소된 이체는 이력이 아니다.
  그래서 신규 수취인에게 보낸 고액 이체가 보류된 뒤 같은 금액을 다시 보내도 또 걸린다.
- 기간 제한이 없다. 몇 년 전 한 번 보낸 적이 있으면 영구히 기존 수취인이다.
- 임계 미만의 소액을 한 번 보내 완료시키면 이후 고액 이체가 이 규칙을 통과한다(알려진 우회 경로).

## 기본 설정값 요약

```properties
ibank.fraud.enabled=false                    # 기본 비활성이었음
ibank.fraud.velocity-window-minutes=5
ibank.fraud.velocity-max-outgoing=5
ibank.fraud.night-high-value-min=5000000
ibank.fraud.night-start-hour=0
ibank.fraud.night-end-hour=5
ibank.fraud.new-payee-high-value-min=3000000
```

## 기존 테스트가 검증하던 것

`base-ibank` 태그의 `src/test/java/com/ibank/fraud/`에 있던 테스트다. B로 옮긴 뒤에도 같은 경계를 확인하면 된다.

- 신규 수취인 고액 이체는 보류되고 자금이 이동하지 않는다.
- 임계치 미만 이체는 정상 완료된다.
- 심야 구간: 자정 횡단 구간(23~6시)의 자정 전후 발동, 구간 바깥 미발동, 같은 날 구간(0~5시), 빈 구간(start == end).
- 보류 후 승인·반려·동시 처리·승인 시점 잔액 부족. 이 부분은 ibank의 내부 실행·취소 API 테스트로 옮겨진다.

**기존 테스트에 없던 것**: VELOCITY 규칙의 임계 경계(5건·6번째)와 "소액 선이체 후 고액" 우회 경로는 테스트가 없었다.
위 설명은 코드만 읽고 정리했으니, B에서 구현할 때 이 둘은 테스트를 새로 만들어 확인해야 한다.
